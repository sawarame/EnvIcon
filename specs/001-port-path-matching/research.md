# 技術調査・設計判断書 (Research): ポート番号・URLパス対応の環境マッチング

**対象機能**: [spec.md](./spec.md) (`001-port-path-matching`)
**作成日**: 2026-11-07

---

## 1. URLパターンのパース・正規化・標準ポートの扱い

### Decision（決定事項）
通常モード（`isRegex: false`）の入力文字列は、以下の手順で解析・バリデーション・正規化する：
1. クエリパラメータ（`?...`）およびハッシュフラグメント（`#...`）が存在する場合は先頭から切り落とす。
2. スキーム（`^[a-zA-Z][a-zA-Z0-9+.-]*://`）が含まれる場合は、`http://` または `https://` のみを有効とし、それ以外のスキーム（`ftp://`, `chrome://` 等）はバリデーションエラーとする。スキーム省略時は解析用に一時的なプレフィックスを補って構文解析しつつ、入力文字列上の明示ポート指定を個別検証する。
3. ホスト名は小文字化し、既存のラベル構文規則（英数字・ハイフン・ドット、または IPv6 ブラケット表記、先頭・末尾のドット/ハイフン禁止、連続ドット禁止）で検証する。
4. ポート番号が明示されている場合は `1〜65535` の10進整数であることを検証する。また、ブラウザの WHATWG URL 標準表現と整合させるため、`http://` における `:80` や `https://` における `:443` は標準ポート省略形へ正規化し、さらに判定時にも対象ページの実効ポート（`location.port`、および明示 `:80`/`:443` パターンとの比較時はプロトコル既定ポート）を考慮して不一致を防止する。
5. パス部分はケース（大文字・小文字）を維持したまま末尾の連続スラッシュ（`/`）を除去する。パスが `/` のみの場合は空文字（パス指定なし）として正規化する。最終的に保存される文字列は `hostname[:port][/path]` 形式となる。

### Rationale（選定理由）
- ブラウザのアドレスバーからコピー＆ペーストした文字列（`https://Example.COM:8080/stg/?a=1#top`）をそのまま貼り付けてもエラーにならず、意図通りの `example.com:8080/stg` へ正規化できるため。
- 標準の `new URL()` だけに頼ると、プロトコル省略入力時に仮付与したプロトコルによって `:443` だけが残る・`:80` だけが消えるといった非対称性や、不正ポート文字列のエラー判別しづらさが生じるため、明示的なポート検証と組み合わせるのが最も堅牢である。

### Alternatives Considered（検討した代替案）
- **正規表現のみで URL 全体をパースする案**: IPv6 アドレス（`[::1]:3000/app`）や国際化ドメイン（Punycode 変換）のエッジケースで破綻しやすいため却下。標準 `URL` パーサーと事前トークン検証の併用を採用した。
- **パスの末尾スラッシュを区別する案**: Web サーバーやルーティングフレームワークによって `/stg` と `/stg/` がリダイレクトされるケースが多く、環境識別において両者を別環境にする実用上の利点がないため、末尾スラッシュ除去で統一した。

## 2. 優先順位（詳細度: Specificity）の決定アルゴリズム

### Decision（決定事項）
対象ページに一致したすべての有効パターンに対して、以下の優先度キーを上から順に比較し、最も優先度の高い単一の環境・パターンを採用する：
1. **階層レベル (`tier`)**:
   - `3`: パス指定あり（通常パターンでパスが存在する、または正規表現パターンに `/` が含まれる）
   - `2`: ポート指定あり・パスなし（通常パターンでポートのみ存在する、または正規表現パターンに `/` が含まれず `:` が含まれる）
   - `1`: ホスト名のみ（通常パターンのホスト名のみ、または正規表現パターンに `/` も `:` も含まれない）
2. **ルール種別 (`isExactRule`)**: 同一階層レベル内では、通常パターン（`1`）を正規表現パターン（`0`）より優先する。
3. **パスの深さ (`pathSegmentCount` → `pathLength`)**: 通常パターン同士でともにパスを持つ場合、スラッシュ区切りのセグメント数が多い方（同数ならパス文字数が長い方）を優先する。
4. **パス付きパターンでのポート有無 (`hasPort`)**: 同一パスの通常パターン同士（例: `localhost:3000/stg` と `localhost/stg`）では、ポート指定あり（`1`）をポート指定なし（`0`）より優先する。
5. **定義順序 (`envIndex` → `patternIndex`)**: 上記すべてが同一の場合は、`environments` 配列のインデックスが小さい方（上から順）、さらに同一環境内では `hostnames` 配列のインデックスが小さい方（上から順）を採用する。

### Rationale（選定理由）
- `FR-008` の要件を完全に満たし、リスト上位の `PROD` に広域の `example.com` を置いたまま下位の `STG` に `example.com/stg` や `example.com:8080` を追加しても、環境の並び替えなしで直感通りに動作するため。
- 比較キーが全順序（Total Order）を形成するため、どのような設定の組み合わせでも曖昧さなく `O(総パターン数)` の1パス走査で一意の結果が得られる。
- 一致結果に `envIndex` と `patternIndex` を保持させることで、オプション画面の URL チェッカー（`FR-014`）における「採用された1行のみのハイライト」を重複ロジックなしで実現できる。

### Alternatives Considered（検討した代替案）
- **環境の並び順のみを優先し、環境カードのドラッグ＆ドロップ並び替えを追加する案**: あるサイトでは `PROD` が親ドメイン・`STG` がサブパス、別のサイトでは `DEV` が親ドメイン・`PROD` が別ポートといった複合ケースを1つの環境順で表現できないため却下。
- **正規表現を常に通常パターンより優先する案**: `^.*\.example\.com$` のような広域正規表現を登録した際、個別サブドメイン `prod.example.com` の通常指定が負けてしまうため、同一階層内では具体的な通常指定を優先する設計とした。

## 3. 正規表現（Regex）モードの後方互換マッチング

### Decision（決定事項）
`isRegex: true` のパターンを評価する際は、以下の2段階判定を行う：
1. 対象ページの `hostWithPort + pathname`（例: `localhost:3000/stg/users`、ルート `/` の場合は `localhost:3000/` とパスを除いた `localhost:3000`）に対して正規表現をテストする。
2. パターン文字列内に `:` および `/` のいずれもが含まれない場合（例: 既存の `^.*\.local$` や `^stg-.*`）に限り、対象ページの `hostname` 単体（ポート・パスなし、例: `myapp.local`）に対しても正規表現をテストし、いずれかが真であれば一致とする。

### Rationale（選定理由）
- 既存バージョンで推奨・案内されていた `^.*\.local$` のような末尾アンカー（`$`）付きのホスト名正規表現が、パス（`/dashboard`）やポート（`:3000`）の存在によって不一致になる破壊的変更を防ぐため（`FR-007`, `SC-003`）。
- 一方で、新しくポートやパスを意図して `:` や `/` を含めて記述された正規表現（例: `^localhost:300[0-9]/admin$`）に対しては `hostname` 単体へのフォールバックを行わないため、意図しない誤マッチも起きない。

### Alternatives Considered（検討した代替案）
- **常にフルURL（`https://...`）に対してのみテストする案**: 既存の `^` や `$` を使ったすべてのホスト名正規表現が動作しなくなるため却下。
- **正規表現の対象フィールドを選択する設定フラグを追加する案**: `SyncData` スキーマおよび1行入力UIが複雑化し、`FR-001` のシンプルさを損なうため却下。

## 4. SPA（ページ再読み込みなしの画面内遷移）の非破壊検知

### Decision（決定事項）
ホストページのグローバル環境（`History.prototype` 等）を一切書き換えず、以下のハイブリッド方式で URL 変化を検知する：
1. **Service Worker (`src/background.ts`) からの通知**: `chrome.tabs.onUpdated` リスナーで `changeInfo.url` の変化を検知した際、ツールバーアイコンの再描画とあわせて対象タブへ `{ type: "URL_CHANGED", url: changeInfo.url }` メッセージを送信する。
2. **Content Script 側の URL 監視モジュール (`src/features/url_observer.ts`)**: コンテンツスクリプト側で `chrome.runtime.onMessage`（`URL_CHANGED`）およびブラウザ標準の `popstate` イベントを購読し、直前に評価した `location.host + location.pathname` と比較して実際にホストまたはパスが変化していた場合のみ、`src/content.ts` 経由で各機能モジュール（Favicon・ページ内バッジ・コンソールログ）の `refresh*` 関数を呼び出す。

### Rationale（選定理由）
- プロジェクト憲章（`constitution.md` 原則 I・III）により、ホストページの DOM やスクリプト環境への破壊的介入は厳禁であり、また `src/content.ts` は薄いオーケストレーターに保つ必要があるため。
- Chrome の `tabs.onUpdated` はホストページ内の `history.pushState` / `replaceState` に対してもブラウザネイティブで即座に `changeInfo.url` を発火するため、Main World へのスクリプト注入（モンキーパッチ）なしで確実かつ安全に検知できる。さらにクエリ（`?`）やハッシュ（`#`）のみの変化時は `host + pathname` 差分比較によって不要な再描画をスキップできる。

### Alternatives Considered（検討した代替案）
- **Main World に `<script>` を注入して `history.pushState` / `replaceState` をラップする案**: ホストサイトのルーターやセキュリティ機構（CSP `script-src`）と衝突するリスクがあり、憲章原則 III に抵触するため却下。
- **`setInterval` ポーリングのみで URL 変化を監視する案**: 応答遅延が生じるか、周期を短くすると全タブで常時無駄なタイマー負荷が発生するため却下（既存の Favicon 3秒チェックは DOM 書き換え対策のセーフティネットとしてのみ維持する）。

## 5. クイック操作ポップアップの粒度とロック判定

### Decision（決定事項）
- ポップアップの表示・ワンクリック環境割り当て・解除・サイト単位の一時OFFは、すべて対象タブの `hostWithPort`（`url.host.toLowerCase()`：標準ポート時は `example.com`、非標準ポート時は `localhost:3000`）を単位とする。
- `SessionData.disabledHostnames` 配列にはこの `hostWithPort` 文字列を保存する（セッション限定データのため既存ユーザーデータの移行問題は発生しない）。
- ポップアップ上でワンクリック変更・解除を許可する条件は「現在未一致である」または「一致したパターンが通常モード（`!isRegex`）であり、かつ正規化後のパターン値が現在の `hostWithPort` と完全一致する」場合のみとする。それ以外の一致（正規表現一致、パス付きパターン一致、またはポート付きURLにおけるポートなし親ホスト一致）はすべてロック案内ボックスを表示し、設定画面への誘導を行う。

### Rationale（選定理由）
- ポップアップの「1クリックで迷わず操作できる」UXを維持しつつ、`localhost:3000` と `localhost:8080` を個別に登録・一時ミュートできるようになるため（`FR-010`）。
- 広域ルールやパスルールが当たっている状態でポップアップから削除・変更を行うと、他ページや他ポートの設定まで巻き込んで破壊する恐れがあるため、ロック案内で保護する設計が最も安全である（`FR-011`, `SC-005`）。

### Alternatives Considered（検討した代替案）
- **ポップアップ内にパス編集用のテキストボックスを追加する案**: 幅 `356px` のコンパクトなポップアップ設計（`DESIGN.md` セクション 4）を圧迫し、オプション画面のバリデーション機能を二重実装することになるため却下。
